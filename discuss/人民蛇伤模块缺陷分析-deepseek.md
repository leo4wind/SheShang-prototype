> 基于 `人民蛇伤模块.md`（模块文档）、`docs/journeys/`（流程文档）、`docs/data-flow.md`（数据流文档）、`docs/page-inventory.md`（页面清单）、`src/`（前端原型代码）交叉比对。

## 一、文档内部缺陷（模块文档 vs 其他文档）

### [文档] 1. 数据治理流程顺序颠倒 — P0

**模块文档现状**：
```
数据落库 → 数据清洗 → 脱敏 → 结构化映射 → 质量控制
```

**正确流程**（`docs/data-flow.md` 评审已修正）：
```
落库 → 脱敏 → 清洗 → 映射 → 质控 → 锁定
```

**评审修正原因**：数据落库后**立刻脱敏**，确保后续治理流程（清洗、映射、质控）接触的都是脱敏数据，降低泄漏面。清洗（去重/校验）不依赖明文身份信息，脱敏后仍能完成。

**影响**：若按文档旧流程实现，清洗阶段接触明文敏感信息——安全层面倒退。

---

### [文档] 2. "救助"错误归入"质控模块" — P0

**模块文档现状**：
```
质控模块（医生端PC/APP）
  ├ 培训 v2
  ├ 救助 v1    ← 描述：远程查看小程序端数据，人工确定病症
  └ 蛇伤判定标准 v2
```

**正确归属**（`docs/journeys/journey-1-emergency.md`）：
```
医生端 · 救助工作台（主线1 阶段C）
  ├ 救助工作台  P201  v1
  ├ 患者实时视图 P202  v1
  ├ 自救指引推送 P203  v1
  └ ...
```

**分析**："救助 v1"说的是**接诊医生远程查看患者求救信息**，这是蛇伤急救流程（主线1），不是数据质量控制。真正的质控模块是**内网数据管理员**的职责：自动校验→质疑→答疑→锁定。

**影响**：导致后续页面路由、权限设计走偏——"救助"对应的 P201/P202/P203 在代码中确实属于医生端（`nav-config.ts`），但如果参考模块文档就会归错地方。

### [文档] 3. 缺失"冷热双通道"架构设计 — P1

**模块文档现状**：完全没有提及。

**文档依据**（`docs/data-flow.md` §冷热双通道分流）：

| 通道 | 数据源 | 处理方式 | 目标存储 | 用途 |
|---|---|---|---|---|
| **热通道** | 小程序求救、120出车、医生录入 | 轻量清洗 + 脱敏 | DH 实时只读库/缓存 | 急救秒级调阅 |
| **冷通道** | HIS/LIS/PACS、旧专病库 | 完整治理管线 | D1 专病库 | 结构化学术档案 |

模块文档只写了"对接HIS/LIS/PACS等获取数据 v2"和"数据治理 v3"两条独立描述，没有说明**同样的数据可以走不同路径**来满足两个截然不同的需求（实时救助 vs 完整治理）。

**影响**：评审已经确认这是关键架构决策，模块文档作为"模块定义"必须体现。

---

### [文档] 4. 缺失"外网→内网隔离通道"设计 — P1

**模块文档现状**："问题记录"中提到了"内网外网数据能否混用"，但正文没有任何隔离策略。

**文档依据**（`docs/data-flow.md`）：
> C端小程序在外网（公网），治理与专病库在内网。两者之间走专门的隔离通道（边界脱敏 + 防火墙 + 审计），**不允许C端直连内网**。

代码中 `IngestPage.vue` 已有体现（黄色 Alert："C端来源已标记「外网」"），但模块文档完全没有。

**影响**：评审时容易被质疑"C端数据怎么进内网"。

---

### [文档] 5. 质量控制缺失"自动校验"环节 — P1

**模块文档现状**：
```
质量控制
  质疑，答疑    ← 全是人工
  审核
  锁定
```

**文档依据**（`docs/journeys/journey-2-data.md` 阶段F）：

| 步骤 | 内容 |
|---|---|
| **15. 自动校验** | 逻辑性检查（出院日期 < 入院日期）+ 配置校验（血压为负、心率为0等） |
| 16-17. 人工质疑 | 质控工作台看校验报告 → 对可疑数据发起质疑 |
| 18. 医生答疑 | 接诊医生回答质疑 |
| 19-20. 审核锁定 | 审核答疑结果 → 锁定入库 |

模块文档只描述了后半段（人工），缺失了**自动校验**这个核心前置环节。

---

### [文档] 6. 质量控制缺失"D2原文查阅"机制 — P1

**模块文档现状**：未提到。

**文档依据**（`docs/journeys/journey-2-data.md` 阶段F步骤17）：
> 工单详情页支持「查阅 D2 原文」按钮（走独立审计日志），可看到原始病历文本/报告单截图，避免脱敏后判不清是数据错误还是脱敏误伤。

**代码现状**（`src/views/intranet/QcTicketPage.vue`）：

### [代码] 14. 质控体系不具备"脱敏后复核"能力 — P1

**关联问题**：第13条的直接后果。

`docs/data-flow.md` 描述：
> 质控人工质疑时能调阅原始病历原文/报告单截图来复核（D2对象存储，走独立审计）

没有D2查阅能力，质控流程中判不清"是数据本身错误还是脱敏误伤"：
- 例：自动校验发现"心率=0"，这是真实数据采集出错还是脱敏时把数值也掩码了？
- 例：NLP抽取的"蛇种"置信度低，需要看原文确认

### [代码] 15. 等待页和实时视图的事件降级逻辑有边界风险 — P2

**文件**：`src/views/patient/WaitingPage.vue` L15-L16、`src/views/doctor/PatientRealtimePage.vue` L15-L16

**代码逻辑**：
```typescript
const eventId = computed(() => {
  const id = route.params.id as string
  if (id && id !== 'demo') return id
  // 回退到activeEvents[0]
  return rescue.currentEvent?.id ?? rescue.activeEvents[0]?.id ?? ''
})
```

**问题**：当 URL 参数是 `demo` 或不存在时，回退到 `activeEvents[0]`（最新事件）。这意味着：
- 如果医生同时在处理多个患者，点菜单进入等待页可能看到**错误患者**
- `activeEvents` 只过滤了 `discharged`，不区分医生归属

**建议**：在医生端加 `assignedDoctor` 过滤，或者至少显示"当前选中的是最近事件的回退"提示。

---

### [代码] 16. 演示模式推送计数器无实际推送逻辑 — P2

**文件**：`src/layouts/AppLayout.vue`

**代码**：
```html
<span v-if="demoMode" class="push-counter">
  <el-icon><BellFilled /></el-icon>
  推送计数 {{ pushCount }}

```

`pushCount` 来自 `useAppStore()`，但没有任何代码给它赋值。`journey-4-care.md` 要求在演示模式下展示"推送计数器"，让评审者看到4条主线没有触发轰炸。目前计数器永远是0，演示失去意义。

### [代码] 18. 治理流程页面间缺乏串联导航 — 建议

**文件**：`src/views/intranet/` 下的治理页面群

| 页面 | 在治理管线中的位置 |
|---|---|
| P301 数据接入监控 | 阶段A |
| P303 落库总览 | 阶段B |
| P306 脱敏规则管理 | 阶段C |

**建议**：在页面顶部加一个小型步骤条（例如：`接入 → 落库 → 脱敏 → 清洗 → 映射 → 质控 → 锁定`），高亮当前所在步骤。参考 `WaitingPage.vue` 的 `el-steps` 模式。
